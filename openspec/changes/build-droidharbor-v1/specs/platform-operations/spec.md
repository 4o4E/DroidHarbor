# Spec Delta

## Purpose

让设备池以可重复部署和维护的方式长期运行，覆盖 Windows 原生及 Linux 平台与 ADB 双容器的持久化、启动恢复、网络和版本合同，并通过真实设备与浏览器测量建立发布证据，而不将规划或构建成功当作产品可用。

## ADDED Requirements

### Requirement: 双部署与单平台服务
产品 SHALL 交付 Windows 原生服务及 Linux Docker Compose 部署；平台由一个服务统一提供网页、API、租约网关和投屏。Linux SHALL 分别运行平台与 ADB，平台更新不要求重启 ADB；不以多宿主调度或多副本共享数据库替代首版交付。

#### Scenario: Windows 原生部署
- **WHEN** 管理员按交付说明配置凭证、证书、数据目录和 ADB 后启动 Windows 服务
- **THEN** 平台能随系统启动、输出运行状态并服务 USB/Wi-Fi 手机，不要求常驻 Python/Node 业务运行时

#### Scenario: 单独更新平台容器
- **WHEN** Linux 管理员更新或重启平台容器而保留 ADB 容器运行
- **THEN** ADB 不被要求同时重启，但平台旧租约仍按重启政策失效并回收

#### Scenario: Windows 前台试用包
- **WHEN** 用户将 Windows amd64 包解压到独立可写目录，初始化管理员并用已有部署参数从 CMD 启动
- **THEN** 单个服务 EXE 提供内嵌网页、API、网关及媒体，scrcpy-server 随 EXE 提供；不需要源码、Node/Go 或独立静态目录，ADB 由外部提供且不被平台替换，CMD 保留真实退出码；打包工作不承担域名/证书或网络基础设施配置

#### Scenario: 客户端与服务端独立分发
- **WHEN** 发布 Windows amd64 版本
- **THEN** 构建生成独立命名的服务端和客户端 ZIP，各有角色专属说明；服务端包含平台 EXE、启动和管理员初始化入口，客户端包含 CLI 与产品 Skill，双方包不混装另一角色的程序或入口，人工网页使用不要求安装客户端

### Requirement: ADB 接入与热插拔可恢复
两种部署 SHALL 明确 ADB 启动责任、USB 权限、无线配对及授权材料位置；同一 USB 设备不得被多个服务端 ADB 实例争用。Linux 部署 MUST 验收容器运行期间的真实设备热插拔，不仅是首次启动可见。

#### Scenario: 容器运行后重新插入 USB
- **WHEN** 手机拔出再插入，系统产生新的设备节点
- **THEN** 按部署说明配置的 ADB 容器能重新发现并授权使用该手机，平台正确更新状态且不重复登记

#### Scenario: ADB 容器单独重启
- **WHEN** ADB 容器重启而平台未重启
- **THEN** 授权材料保留，旧连接报告中断；未到期租约不被隐式延长或换设备，恢复后需显式建连且不重放旧操作

### Requirement: 内网 VPN 认证及媒体可达性
平台 SHALL 通过内网/VPN 的认证加密入口使用，部署须明确 HTTPS 和媒体网络配置；原始 ADB 管理端口及手机原始无线端口 MUST NOT 作为调用方旁路。不能仅凭网页可打开就宣称视频可用，不隐式部署公网穿透或 TURN。

#### Scenario: 信令可达但媒体被阻断
- **WHEN** 浏览器能访问 HTTPS，而 VPN/防火墙或容器地址导致媒体不可达
- **THEN** 平台报告媒体连接失败及可定位信息，不伪报投屏成功或静默切换未经批准的备用路线

#### Scenario: 调用方试图访问原始 ADB
- **WHEN** 调用方尝试绕过租约入口连接服务端 ADB 管理端口
- **THEN** 产品部署配置不为其开放该端口，并明确手机网络需避免直连旁路；不把随机端口当作访问认证

### Requirement: 持久化与一致性备份
产品 SHALL 持久化设备配置、标签、身份、租约记录和画质配置，Linux 中平台数据与 ADB 授权材料分别持久化。备份 MUST 是一致性快照，恢复 MUST 不复活旧租约；数据库不保存视频或明文任务凭证。

#### Scenario: 更换容器
- **WHEN** 平台或 ADB 容器替换但保留对应持久化卷
- **THEN** 设备配置与授权材料仍可恢复，不需因临时容器文件丢失重新登记所有设备

#### Scenario: 恢复运行中产生的备份
- **WHEN** 管理员按交付说明备份并恢复平台
- **THEN** 数据一致且 schema 可识别，旧租约失效并经过回收，不把历史 active 状态重新开放给旧任务

### Requirement: 启动恢复和错误可见
平台启动 SHALL 先完成单实例、数据版本、旧授权撤销及资源核验，再允许新分配；配置无效、数据库损坏或未知 schema MUST 明确失败，不静默创建空库覆盖原数据。回收失败的设备仍须保持不可分配。

#### Scenario: 数据版本不受支持
- **WHEN** 启动使用无法识别的数据库版本
- **THEN** 服务明确拒绝运行并保留数据，不自动降级、重建或伪报健康

#### Scenario: 崩溃遗留平台资源
- **WHEN** 上次平台进程在资源创建后异常退出
- **THEN** 新进程核验归属并定向回收，归属不明则隔离，不全局杀 ADB 或任意手机进程

### Requirement: 版本合同与实际支持矩阵
每个发布 SHALL 声明服务、CLI、产品 Skill、API/ADB 协议及依赖的兼容版本，并列出实际验收的操作系统、架构、手机和浏览器矩阵。必要版本不匹配 MUST 明确拒绝，不能以成功编译代替运行支持。

#### Scenario: 不兼容的 CLI 接入
- **WHEN** CLI 要求平台未支持的必需协议版本
- **THEN** 平台返回明确不兼容，不接受部分握手后伪装可用，也不后台升级调用方

#### Scenario: 发布浏览器支持声明
- **WHEN** 首版声明桌面 Chrome/Edge 和 Android Chrome 支持
- **THEN** 发布证据包含对应真实网页操作与媒体测试，不用桌面截图替代 Android 浏览器验证

### Requirement: 运行记录不泄露业务秘密
平台 SHALL 提供基本存活/就绪状态和结构化运行记录，足以定位租约、回收、设备及媒体故障；记录 MUST NOT 保存凭证、完整 shell 正文、剪贴板文本或视频内容。状态事件不是持久状态的替代品。

#### Scenario: 设备被隔离
- **WHEN** 平台资源回收失败导致设备不可分配
- **THEN** 管理员能看到对应设备、回收原因和失败结果，不需读取敏感命令正文来定位状态

#### Scenario: 试用运行故障可定位
- **WHEN** 启动、存储、ADB 发现、采集、传输或后台资源清理失败
- **THEN** 控制台和有界轮转文件均输出故障事件及关联 ID、阶段/错误码和安全的原因链；OS 错误保留 errno，SQLite 保留结果码，原始设备输出和 SQL 参数不进入日志；HTTP panic 记录安全调用栈后保持异常请求失败

#### Scenario: 日志输出本身失败
- **WHEN** 日志文件无法创建，或运行中写文件失败
- **THEN** 创建失败使服务非零退出，运行中写失败明确输出到 stderr，不悄悄丢失诊断；正常日志仍显示在控制台


### Requirement: 真实性能测量先于数值验收
项目 SHALL 先测量再确认性能数值门槛，分别记录局域网/VPN、Windows/Linux 部署及单/多观看者条件。MUST 记录实际画质、可见操作延迟、建流时间、CPU/内存/网络和稳定性行为，不将换语言、估算带宽或代理压测冒充真机达标。

#### Scenario: 首轮测量
- **WHEN** 在现有约 3 台手机上运行首轮负载与异常恢复场景
- **THEN** 记录设备/宿主/网络条件、默认长边 1920/30 fps/4 Mbps 及实际输出数据，并据此提交数值门槛评审，不预先声称达到 200 ms 或固定连续运行时长

#### Scenario: 尚无十台实机
- **WHEN** 使用代理压测评估目标十台容量但没有十台真实编码设备
- **THEN** 报告明确区分网关/网络压测与手机编码实测覆盖，不宣称已完成十台真机容量验收

### Requirement: 首版完成以端到端结果为准
首版交付 MUST 完成设备池、真实原生 adb、显式续租和回收、产品 Skill、网页交互、可调共享画质及两种部署的验收；不能以规划文件、编译、mock 或局部骨架替代完成，不重新安排参考项目试用。

#### Scenario: 准备发布首版
- **WHEN** 团队检查发布条件
- **THEN** 每个已确认范围有对应实际运行证据及明确结果，未完成的真机或浏览器场景不能标记通过，也不把 Appium/uiautomator2 列为当前兼容成果
